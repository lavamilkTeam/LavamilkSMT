# 上位机自身更新服务

`host-updater` 负责 Linux 上位机自身的应用和系统固件更新，规划使用 Go，独立于
`console/backend`、Python `controller` 和 `mcu-updater` 运行。

**当前状态：仅建立目录和职责约定。尚无 Go 模块、可执行程序、更新接口或安装功能。**
本目录不表示系统已经支持在线升级或断电回退。

## 更新范围

- 应用更新：console、controller、preview 及配套应用资源，按发布清单声明的组件与依赖升级。
- 系统固件更新：板型对应的 Linux 系统镜像、内核或设备树，由独立的板级安装适配器处理。
- MCU 固件交给 [mcu-updater](../mcu-updater/README.md)，本服务不操作 ST-LINK。
- updater 自身的替换需要独立安装器或受控重启机制；不能直接覆盖正在执行升级的程序。

第一阶段先实现应用更新。系统固件安装需确认实际板型、分区、启动方式和恢复机制后再开发，
不能把应用目录切换视为系统镜像的原子更新，也不能预设现有硬件支持 A/B 分区。

## 计划代码组织

以下为实现时的 Go 目录约定，目前尚未生成代码和空包：

```text
host-updater/
├── go.mod
├── cmd/smt-host-updater/main.go   # 入口、配置与依赖组装
└── internal/
    ├── update/                  # 更新事务、持久状态与恢复
    ├── release/                 # 版本清单、下载、来源与完整性校验
    ├── application/             # 应用版本安装、切换及健康检查
    ├── systemimage/             # 系统镜像安装的板级适配器
    ├── maintenance/             # controller 维护握手与共享更新互斥
    └── api/                     # 面板请求、任务状态与日志
```

首次实现时建立独立 `go.mod`，不与 console 后端或 mcu-updater 共用进程。
接口约定保存在根目录 `protocols/`，systemd 服务模板放 `deploy/`。

## 更新流程约定

1. 查询已发布版本，固定目标版本与发布清单，核对板型、CPU/系统 ABI 和组件兼容性。
2. 下载到临时目录，校验来源和文件完整性，检查磁盘空间；不在更新过程中追随移动的分支头。
3. 与 controller 协调设备进入维护状态，取得两个 updater 共用的更新互斥权，持久记录事务。
4. 应用更新按依赖顺序停止相关服务、安装版本并切换；系统镜像更新走明确的板级安装流程。
5. 执行健康检查并记录结果；失败时按已验证的恢复方案处理，状态未知时保持维护状态。
6. 恢复控制服务后先核对真实设备状态，由明确操作重新回零或恢复工作，不自动续跑贴装。

controller 停机、上位机重启或浏览器断开都不能丢失维护约束。首次实现需同时补齐
持久记录与启动恢复检查，不能只依赖内存中的“升级中”标志。

开发缓存和日志使用 `local/host-updater/`；正式部署使用独立运行数据目录。
共享互斥记录与 MCU 更新服务统一约定。用户工程、标定和密钥独立保留，不由新版本发布包覆盖。

当前 `tools/install_target_console.sh` 是手动部署工具，可作为应用安装适配的参考，
不能视为已具备整机升级事务、统一维护互斥或自动回退。
